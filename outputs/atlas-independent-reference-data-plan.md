# ATLAS independent reference data access plan

**Prepared:** 2026-11-02  
**Status:** multiple sources screened; no candidate-area package yet supplies qualifying event-matched, independently governed labels across the 16 AOIs.

## Candidate benchmark: OPERA DSWx-S1 CalVal Database V1

NASA/JPL lists a public OPERA DSWx-S1 calibration/validation database containing classification items, a reference document, and validation results. Data.gov reports one archived granule, `OPERA_DSWx-S1_V1_CalVal_DB.zip`, about 181.6 MB, with a September 2021 temporal extent and a broad global bounding box (−160.1° to 146.3° longitude; −71° to 59.2° latitude). Its spatial envelope includes the 16 candidate cities, but that does **not** prove that any candidate has a reference label in the package.

Primary records:

- [NASA/JPL Data.gov catalog record](https://catalog.data.gov/dataset/opera-dynamic-surface-water-extent-from-sentinel-1-calval-database-version-1) — describes classification items for algorithm calibration and validation and links example notebooks.
- [PO.DAAC OPERA DSWx-S1 V1 dataset page](https://podaac.jpl.nasa.gov/dataset/OPERA_L3_DSWX-S1_V1) — documents the OPERA product, public/protected S3 prefixes, and Earthdata Login requirement for protected product files.
- [OPERA CalVal example repository](https://github.com/OPERA-Cal-Val/calval-database) — contains tools and example notebooks; archived in 2022 and its README leaves database organization/access work marked “In Progress,” so examples alone do not establish a current, reproducible label-delivery path.
- [NASA earthaccess authentication guide](https://earthaccess.readthedocs.io/en/latest/user/explanation/authenticate/) — data search is available without login, but downloading or streaming NASA DAAC data requires a free Earthdata Login account.

## Access and interpretation gates

1. Confirm the account can access PO.DAAC and retrieve the CalVal ZIP through Earthdata Login. The CMR metadata query succeeds anonymously; the corresponding granule link points to `podaac-ops-cumulus-protected`. No Earthdata credentials are configured in ATLAS, and none should be committed or sent in chat.
2. Inspect the ZIP's reference document and item manifest before analysis. Record label source, annotator, source-image sensor/date/resolution, georegistration error, label-generation process, spatial footprint, and licensing/attribution. Until those fields are verified, treat the CalVal items as a candidate reference source, not independent truth.
3. Intersect actual label footprints and dates with each fixed 25 × 25 km ATLAS AOI and prespecified events. Report per-city reference counts and missingness. The catalog's global bounding box and one-month temporal extent are not evidence of per-area coverage.
4. Freeze a label holdout before parameter tuning. Keep label-derived algorithm development cases separate from the final held-out event/site assessment. Never claim accuracy from comparison to labels that were used to tune the detector.
5. Use the same rule in every enrolled site. If the database does not supply enough spatially and temporally matched references, obtain independently governed local agency/field references or defer the site; do not substitute unvalidated CMR metadata or raw backscatter for water labels.

## Alternate archive: Sentinel-1 RTC, not a replacement label or water product

Microsoft Planetary Computer exposes anonymous STAC search for its Sentinel-1 Radiometrically Terrain Corrected collection; its data-authentication documentation says SAS tokens can be obtained anonymously. A reproducible all-area screen of `sentinel-1-rtc` over the same 2024-09-01 to 2026-11-02 period returned 55–442 scene items and 55–280 distinct metadata dates per AOI. No exact acquisition date was common to all 16 boxes; 25 of 27 represented year-month bins contained at least one scene for every area. This demonstrates archive-level SAR availability, with materially different scene counts, not comparable valid-pixel observation coverage. The run is recorded in `outputs/atlas-sentinel1-rtc-coverage-audit.json` and reproduced by `scripts/audit_sentinel1_rtc_coverage.py`.

These are Sentinel-1 RTC radar-backscatter assets, not OPERA DSWx-S1 water-class rasters. Because both use Sentinel-1 observations, RTC is a separate processing product but not an independent sensor source for validating OPERA classifications. It may support a separately specified SAR-method feasibility study after radiometric/terrain QA and independent reference validation; it cannot be counted as equivalent OPERA water observations or satisfy the current QA/label gate.

Primary sources: [Planetary Computer STAC API](https://planetarycomputer.microsoft.com/docs/reference/stac/), [Planetary Computer data-access tokens](https://planetarycomputer.microsoft.com/docs/concepts/sas/), and [Sentinel-1 RTC collection explorer](https://planetarycomputer.microsoft.com/explore?d=sentinel-1-rtc).

## OPERA pixel QA route through Google Earth Engine

The official Earth Engine catalog exposes the same OPERA DSWx-S1 V1 product as `OPERA/DSWX/L3_V1/S1`, openly shared at 30 m and with catalog availability through 2026-10-28 in the 2026-11-02 snapshot. Its `BWTR_Binary_water` band documents 0 as valid non-water, 1 as water, 250 as HAND-masked, and 251 as layover/shadow-masked; fill/no-data is not valid. This provides a practical route to screen true valid-pixel coverage without relying on collection-item counts. Earth Engine access itself requires an enabled and registered Google Cloud project and a commercial/noncommercial use decision. That access and eligibility have not been verified for ATLAS.

The owner-run Code Editor diagnostic is prepared at `scripts/earthengine/atlas_opera_pixel_coverage.js`, with instructions in `outputs/atlas-earth-engine-pixel-audit-guide.md`. It covers the fixed 16 AOIs, mosaics same-day tiles, reports per-date valid-area fraction and class histograms, and flags dates below 80% AOI validity. The Earth Engine catalog snapshot ends five days before the existing CMR screen, so this pass uses a common window ending 2026-10-28 and reports that cutoff. No Earth Engine execution has occurred; this workflow provides no new coverage result or score credit until its output is reviewed. Even a successful pixel audit would not establish flood-event coverage or independent reference-label adequacy.

Primary sources: [OPERA DSWx-S1 Earth Engine catalog](https://developers.google.com/earth-engine/datasets/catalog/OPERA_DSWX_L3_V1_S1), [Earth Engine access setup](https://developers.google.com/earth-engine/guides/access), and [commercial-use guidance](https://developers.google.com/earth-engine/guides/transition_to_commercial).

## Direct NASA file access and reprocessing control

The official [PO.DAAC collection record](https://podaac.jpl.nasa.gov/dataset/OPERA_L3_DSWX-S1_V1) makes an important distinction for the alternative to Earth Engine: the science data prefix is `podaac-ops-cumulus-protected/OPERA_L3_DSWX-S1_V1`, which requires Earthdata Login and S3 credentials. The matching public prefix contains supporting metadata and browse/checksum material; it does not provide anonymous access to the protected science GeoTIFFs. CMR metadata discovery therefore cannot be treated as file access, and direct S3 listing is not an authentication bypass. The account owner must use Earthdata Login or a registered Earth Engine project before full raster QA can proceed.

PO.DAAC also reports that OPERA reprocessed all affected DSWx-S1 granules acquired **2025-05-20 through 2025-12-09** after a processing anomaly; replacement products are available and users are advised to replace previously downloaded files. Any ATLAS run including those dates must query the current granule records, record the replacement granule ID/product-generation metadata and SHA-256, and avoid stale cached copies. The local analyzer records granule ID, product/software version, retrieval time, source checksum, and analysis-code checksum, but those records only prove provenance if the inputs were retrieved from the current authoritative collection. The Earth Engine diagnostic should be run against its current collection and outputs retained with their execution date; if the collection's reprocessing status cannot be verified for an acquisition, exclude it pending confirmation.

Primary source: [PO.DAAC OPERA DSWx-S1 V1 collection record](https://podaac.jpl.nasa.gov/dataset/OPERA_L3_DSWX-S1_V1), “Direct S3-Access” and product information. Its notice says replacement granules for the 2025 anomaly are available and recommends replacing earlier downloads. The separate Earthdata alert page was unavailable during this check, so this record is the evidence cited here.

## Public label-dataset screens: C2S Microsoft Floods and UFOv2

Two public, manually labeled flood/surface-water datasets were screened against the exact 16 fixed ATLAS AOI boxes on 2026-11-03. The reproducible machine-readable outputs are `outputs/atlas-c2s-flood-dataset-audit.json` and `outputs/atlas-ufo-dataset-coverage-audit.json`; scripts and local geometry/key tests are under `scripts/audit_c2s_flood_dataset.py`, `scripts/audit_ufo_dataset_coverage.py`, and `tests/`.

- The [C2S Microsoft Floods registry](https://registry.opendata.aws/c2smsfloods/) lists 900 Sentinel-1 label chips across 18 events. Within the 16 AOIs, the audit found one label chip, Houston / 2017-08-30: 34,967 valid label pixels (about 3.50 km², 0.56% of the 625 km² AOI), including 277 water pixels. It is one sparse date/event and cannot support balanced area-level validation. The registry lists CC-BY-4.0, while the linked [dataset README](https://radiantearth.blob.core.windows.net/mlhub/c2smsfloods/ms-dataset_README.pdf) states CC-BY-SA-4.0; clarify the applicable license before redistribution. The README also says labels mark water visible in Sentinel-1 with Sentinel-2 visual support, so this is not a fully independent sensor reference to OPERA DSWx-S1.
- The authors’ [UFOv2 Zenodo release](https://zenodo.org/records/23426661) contains 215 PlanetScope visible-surface-water label-chip footprints across 14 events. All 215 metadata records were read successfully; none overlap the 16 fixed AOI boxes. This exact-footprint miss is not a claim that Houston had no observations: the archive includes Houston chips outside the selected 25 × 25 km Houston AOI. Its [paper](https://arxiv.org/abs/2604.23066) and [source repository](https://github.com/Tellman-lab/urbanFloodObservations) describe manually annotated PlanetScope imagery; the labels include pre-existing water and do not distinguish floodwater. The source package is a different sensor from OPERA but gives no matching reference chips for these fixed study boxes.

Neither audit provides held-out event validation, comparable 8+8 coverage, or a score increase. The C2S result establishes only one sparse Houston label overlap; UFOv2 establishes zero chip-footprint overlaps for the current AOIs. Continue seeking locally governed event products or field labels, and apply the same spatial, temporal, licensing, annotation, and sampling gates to every enrolled area.

## Event-reference discovery audit: Copernicus EMS and Global Flood Database

On 2026-11-02, the public [Copernicus EMS API guide](https://mapping.emergency.copernicus.eu/about/how-to-harvest-cems-mapping-data/) and [Rapid Mapping API](https://mapping.emergency.copernicus.eu/about/how-to-harvest-cems-mapping-data/emergency-response-data/) were queried. The all-activation catalog contained 1,068 entries (350 marked flood); a separate public rapid-mapping feed returned 268 entries (90 flood). A coarse screen of AOI extents against each registered 25 × 25 km city box found no intersections in the rapid-mapping feed. The all-activation catalog's approximate centroid screen found one nearby record for Manila, EMSR017 (2012), but a centroid-radius hit is not an AOI overlap and is too old to validate the current observation window. The raw discovery output is `outputs/atlas-cems-event-discovery-audit.json`.

This is a discovery result, not proof that no relevant local event references exist: the feeds differ in scope, catalog extents are not a complete local-event registry, and the rapid-mapping spatial test is deliberately coarse. CEMS provides AOIs, event/activation times, product metadata, source imagery details, and public download links. An intersecting event still needs exact geometry, image-source independence review (exclude same-source Sentinel-1 products from independent validation), reference-label provenance, coverage, and blinded QA before it can qualify. Accordingly, CEMS has not supplied qualifying independent labels for any registered site yet.

The [Google Earth Engine Global Flood Database catalog](https://developers.google.com/earth-engine/datasets/catalog/GLOBAL_FLOOD_DB_MODIS_EVENTS_V1) describes 913 MODIS-mapped events from 2000–2018 at 250 m, sourced from Dartmouth Flood Observatory event records and available under CC BY-NC 4.0. Its maintainers publish point-level validation data in the [project repository](https://github.com/cloudtostreet/MODIS_GlobalFloodDatabase), described as analyst interpretation using Landsat imagery. An exact point-in-AOI audit of the published validation file found eight points in Sacramento and zero in the other 15 candidate AOIs. All eight Sacramento points reference DFO event 4444, reported for 2017-02-16 through 2017-03-03; the Landsat assessment date in the points file is 2018-06-26. The temporal mismatch disqualifies these points as contemporaneous validation for that event, and eight points also fall short of adequate site/event sampling. The event-level metric file reports performance for a much larger event sample, which cannot be attributed to ATLAS's Sacramento AOI. No GFD validation point currently qualifies at any candidate site. Counts, event metadata, and limits are recorded in `outputs/atlas-global-flood-db-validation-audit.json`.

The GFD files may support a historical, coarse-resolution algorithm-method check when an event footprint, acquisition timing, and independent point protocol align. Its 2000–2018 extent, 250 m MODIS resolution, and limited local point coverage mean it cannot validate the current 2024–2026 window or substitute for adequately sampled contemporary independent labels.

## Effect on current claims

No registered site has passed real-raster scene QA or independent label validation. The Texas technical pilot remains outside the 16 candidates and failed its minimum-date gate. This source audit identifies a credible next reference-data lead and clarifies the Earthdata account dependency; it awards no score points and does not validate the candidate sites.
